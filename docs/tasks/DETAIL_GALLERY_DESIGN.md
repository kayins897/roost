## 当前工程事实（独立只读调查）

- `MediaItem` 只有 `coverUrl`，没有截图模型：`src/domain/types.ts:45`。
- 现有封面在编辑器中压缩为 JPEG data URL；封面优化尺寸不适合珍藏、放大的游戏截图：`src/presentation/features/editor/WorkEditor.tsx`。
- 收藏 JSON 上限 100MiB，整个快照通过现有同步保存 IPC 传输，previous / 7 daily 也是整库备份：`desktop/store.ts:7`、`src/infrastructure/repository.ts:19`。
- 当前导出是 JSON Blob，导入是 JSON 校验后整库替换，**不会包含外置图片**：`src/presentation/app/useWorkspaceController.ts:288`。
- 当前 CSP/自定义协议没有任意本地图片读取能力；`qiyu` 协议只服务 dist。不能只加一个 file:// 路径就称为支持：`index.html:6`、`desktop/main.ts:179`。
- 普通保存和生命周期对象展开可以保留扩展字段；“允许未知字段”不等于已有截图结构校验和资产恢复。

## 建议首期范围（待确认后正式接入）

1. Windows、仅手动选择 PNG/JPEG/WebP，可一次多张；不自动扫描 Steam 文件夹，不加入云端、AI 或视频。
2. 按每款游戏保存截图，预览图集、完整大图、左右键切换、可选简短说明、移出相册；首期按添加顺序，不引入截图评级等额外系统。
3. 保留导入原图，另外生成缩略图。**复制成功后，原文件移动或删除都不影响相册**。
4. 图片放在当前数据目录下由应用管理的资产目录；JSON 只存小引用，绝不把大量截图 base64 塞进收藏 JSON。
5. 完整备份按所有者已确认的单文件形式，包含 JSON、被引用的图片和清单；旧 JSON 导入/导出继续兼容，但界面须明确“仅收藏数据，不含截图”。具体归档结构与恢复契约待实现方案评审，尚未实现；不能退回只备份 JSON 的能力冒充完整备份。
6. 移出相册只解除引用，不动用户来源文件。首期不自动清理托管原图，以免已有 previous/daily/导入前备份恢复时缺图；后续明确清理与空间管理再实施。

## 接入设计

建议增量增加可选 `screenshots` 数组，元素仅存稳定截图 ID、受控 asset ID、录入时间、可选说明、尺寸/格式；不记录用户原始绝对路径。数组顺序即展示顺序，不增加第二套排序字段。字段名和结构由实现前数据设计冻结。

- domain：截图结构校验、纯增删/说明补丁、旧库缺省空数组只读展示；不启动补写，不改变分类/完成次数/普通日志。
- infrastructure + 唯一 IPC 契约：异步选择/导入/取消、图片导入结果与受控资产读取；UI 不直接用 fs、桥或任意本地路径。
- desktop：复制到暂存、解码验证、生成缩略图、原子落文件，之后再通过既有修订检查保存 JSON。失败最多留下无引用图片，不留下已经保存但原图不存在的引用。
- 媒体路由：仅按受控 asset ID 返回托管文件；校验路径、类型、大小和跳转，不开放任意目录读取，不泄漏用户来源路径。
- 备份：新完整导出应包含所有当前引用图；恢复先验证完整性并准备资产，再替换快照。旧 JSON 备份保持原义，不伪装含图，也不对旧字段做迁移。
- 删除：保留历史快照引用的资产，避免立即 unlink；以后若做清理，必须遍历 current、previous、daily 和导入前备份的有效引用。
- 导入去重、图片/像素/容量上限需实现前写明；暂不擅自定义每款截图数量限制，也不自动压损原图。

推荐按上述“资料常驻 + 手动相册 + 复制原图 + 含图完整备份”作为一个可验收阶段。其余截图自动扫描、视频、云同步、相册组织后置。
