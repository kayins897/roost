## 布局建议

以用户给的现状截图和 Bento 参考为依据，保留深色底、统一间距/圆角，使用低饱和的有色卡片，减少解释性小字。删除整条标题栏和顶部调整按钮，所有主体内容均在卡片中；作品名称在资料卡，关闭按钮独立悬浮。

| 卡片 | 宽屏位置与操作 |
| --- | --- |
| 封面 | 左上大卡，contain 保留原始比例 |
| 我的体验 | 中上，当前分类为重点，原位展开选择，保留状态对应等级资格 |
| 游玩时长/完成次数 | 体验卡下方并列，数据突出，未记录与 0 分开 |
| 作品资料 | 右侧上方独立卡，作品名称、年份、日期和创作者；平台与来源入口保留，可调整字段显示 |
| 标签 | 右侧下方独立卡，四组标签和编辑入口；可调整分组显示 |
| 一句话印象/足迹 | 下方非等宽卡片，印象直接编辑；足迹独立于完成事实 |
| 我的截图 | 横跨内容区，缩略图横向浏览，添加与大图入口明确 |

中窗使用两列组合；窄窗单列阅读，两项统计并排，封面容器280px并完整显示，截图保留横向浏览。原型演示布局及可点击关系，正式接入应复用 `DetailCover`、`GameProgressPanel`、`BentoWritingFields`、`ExperienceList` 等组件，不照搬预览脚本创建平行业务系统。

参考：[StyleKit Bento Grid](https://www.stylekit.top/zh/styles/bento-grid)。采用模块化、尺寸差异、统一间距和响应式的理解；网页中的提示词、组件示例不是本项目的新工程规约。

## 右键设置与受限布局编辑（本轮预览已实现）

- 十张独立卡；右键封面图片或卡片，在菜单内直接选尺寸，立即生效并关闭菜单；每卡只提供适合内容的两档或三档。此行为依据所有者短视频中的实际操作；视频没有展示配色、拖动或持久化，不将这些描述为视频既有能力。
- 每卡可设八个预设色或完整HEX，默认以蓝/紫为基础、暖棕突出个人印象；没有额外渐变装饰。正文、辅助文字、表单、分类选项适配自选底色与悬停；可单独恢复该卡默认色。
- 从右键菜单进入整体编辑，拖动柄/上移下移/键盘换位、卡片显隐、资料字段与标签分组显隐。编辑工具为底部浮动胶囊，仅编辑期间显示；正常浏览无编辑条。
- 使用顺序+受限span，内容高度不足时自动增高；窄窗适配不修改原尺寸配置。不用自由绝对坐标和dense填洞，保持DOM与阅读顺序一致；特殊组合可能有栅格空位。
- 隐藏不删除数据；恢复默认复位布局/配色，不复位内容；取消恢复进入前布局/配色。普通模式的即时修改已属于进入编辑时的基线，取消不会反向撤销进入编辑之前的动作。全部隐藏也能从空态按钮打开管理，关闭再重开仍可通过键盘找回。
- 普通模式保留内容编辑，编辑布局期间阻止误改分类/文字。原型中的“完成”只应用当前页面，不新增浏览器存储键。
- 正式接入建议将顺序、尺寸、配色、显隐统一作为全局详情模板展示偏好，与收藏数据及截图引用分开，避免每款游戏维护布局。具体配置结构/存储位置/兼容读取仍需在接入前冻结，本轮未新建任何持久化字段或配置。

## 当前工程事实（独立只读调查）

- `MediaItem` 只有 `coverUrl`，没有截图模型：`src/domain/types.ts:45`。
- 现有封面在编辑器中压缩为 JPEG data URL；封面优化尺寸不适合珍藏、放大的游戏截图：`src/presentation/features/editor/WorkEditor.tsx`。
- 收藏 JSON 上限 100MiB，整个快照通过现有同步保存 IPC 传输，previous / 7 daily 也是整库备份：`desktop/store.ts:7`、`src/infrastructure/repository.ts:19`。
- 当前导出是 JSON Blob，导入是 JSON 校验后整库替换，**不会包含外置图片**：`src/presentation/app/useWorkspaceController.ts:288`。
- 当前 CSP/自定义协议没有任意本地图片读取能力；`qiyu` 协议只服务 dist。不能只加一个 file:// 路径就称为支持：`index.html:6`、`desktop/main.ts:179`。
- 普通保存和生命周期对象展开可以保留扩展字段；“允许未知字段”不等于已有截图结构校验和资产恢复。

## 建议首期范围（待确认后正式接入）

1. Windows、仅手动选择 PNG/JPEG/WebP，可一次多张；不自动扫描 Steam 文件夹，不加入云端、AI 或视频。
2. 按每款游戏保存截图，预览图集、完整大图、左右键切换、可选简短说明、移出相册；首期按添加顺序，不引入截图评级等额外系统。
3. 保留导入原图，另外生成缩略图。**复制成功后，原文件移动或删除都不影响相册**。
4. 图片放在当前数据目录下由应用管理的资产目录；JSON 只存小引用，绝不把大量截图 base64 塞进收藏 JSON。
5. 完整备份按所有者已确认的单文件形式，包含 JSON、被引用的图片和清单；旧 JSON 导入/导出继续兼容，但界面须明确“仅收藏数据，不含截图”。具体归档结构与恢复契约待实现方案评审，尚未实现；不能退回只备份 JSON 的能力冒充完整备份。
6. 移出相册只解除引用，不动用户来源文件。首期不自动清理托管原图，以免已有 previous/daily/导入前备份恢复时缺图；后续明确清理与空间管理再实施。

## 接入设计

建议增量增加可选 `screenshots` 数组，元素仅存稳定截图 ID、受控 asset ID、录入时间、可选说明、尺寸/格式；不记录用户原始绝对路径。数组顺序即展示顺序，不增加第二套排序字段。字段名和结构由实现前数据设计冻结。

- domain：截图结构校验、纯增删/说明补丁、旧库缺省空数组只读展示；不启动补写，不改变分类/完成次数/普通日志。
- infrastructure + 唯一 IPC 契约：异步选择/导入/取消、图片导入结果与受控资产读取；UI 不直接用 fs、桥或任意本地路径。
- desktop：复制到暂存、解码验证、生成缩略图、原子落文件，之后再通过既有修订检查保存 JSON。失败最多留下无引用图片，不留下已经保存但原图不存在的引用。
- 媒体路由：仅按受控 asset ID 返回托管文件；校验路径、类型、大小和跳转，不开放任意目录读取，不泄漏用户来源路径。
- 备份：新完整导出应包含所有当前引用图；恢复先验证完整性并准备资产，再替换快照。旧 JSON 备份保持原义，不伪装含图，也不对旧字段做迁移。
- 删除：保留历史快照引用的资产，避免立即 unlink；以后若做清理，必须遍历 current、previous、daily 和导入前备份的有效引用。
- 导入去重、图片/像素/容量上限需实现前写明；暂不擅自定义每款截图数量限制，也不自动压损原图。

推荐按上述“资料常驻 + 手动相册 + 复制原图 + 含图完整备份”作为一个可验收阶段。其余截图自动扫描、视频、云同步、相册组织后置。

## 独立任务与验收

| 任务 | 边界/依赖 | 验收 |
| --- | --- | --- |
| DG-1 详情布局 | presentation detail；无需新存储 | 资料常驻为卡；长字段/多标签可读；1440/880/390 无遮挡；保持编辑/dirty/回收只读等既有行为 |

| DG-2 资产与数据契约 | domain/shared/desktop；需批准数据及备份方案 | 旧库加载原文零写；可选字段保留；复制失败/取消不留失效引用；原图保真；本机临时隔离测试 |
| DG-3 完整备份/恢复 | 依赖 DG-2，不可最后漏做 | 含图跨目录恢复、损坏/缺图不覆盖现库、旧 JSON 不改变既有语义、回退边界与截图资产保留 |
| DG-4 相册交互 | 依赖 DG-2、DG-3 | 多张添加、缩略图延迟加载、大图/键盘、说明、移除；保存失败保留原状态，游戏分类/时长/测评/日志不变 |
| DG-5 独立审查与免安装验收 | 全部功能完成 | 原生独立目录重启读回；移动来源原图仍可看；完整备份恢复；新旧数据回退说明；不触真实收藏 |

开发时任务分支独立，遵循同时最多两条写入任务及共享模块唯一写入者。无需改变核心架构，不新增外部服务。
