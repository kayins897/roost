## 四、ZD-01：右键菜单直接设置优先级和通关评级（第一优先）

### 要解决的具体问题

目前右键选择待体验或已通关后，会另外打开 QuickRankEditor。希望在右键菜单内完成，不再为这个快捷操作弹出第二个居中窗口。保持详情、批量编辑等其他已有入口的用途，不为这项任务重写它们。

先阅读：src/presentation/features/library/ContextMenu.tsx、features/detail/QuickRankEditor.tsx、app/useWorkspaceController.ts、评级领域规则，以及当前等级输入专项。先追踪真实保存和错误返回链路，再改代码。

### 推荐实现方式

- 六个游玩状态保留现有含义。菜单可用紧凑分组，但本次不改变暂时搁置的实际状态或排序语义。
- 右键待体验作品，直接显示“优先级：SSS / SS / S / A / B / C / 未设置”；右键已通关作品，直接显示对应“个人评级”一行，当前选择明确高亮。
- 其他状态选择待体验或已通关后，在同一个菜单内展示对应等级行；不自动打开 QuickRankEditor。状态成功保存后，用户也可以不设等级直接离开。
- 已处于相应状态时，一次点击等级即可保存。选择“未设置”只清除该维度，不清除另一个维度和历史内容。
- 优先级和个人评级沿用现有两个字段；等级变化时，只按原规则处理对应手动排序字段，不改变另一套顺序。
- 持续游玩作品保留已有历史评级，不在本次开放新的评级资格，不自动当作已通关，也不激活额外箔面资格。
- 使用主题 token 和现有按钮风格；小范围新增样式放对应 feature，不追加全局覆盖层。不扩展成整个详情页或全局菜单改版。

### 验收标准

1. 两种等级均可在右键菜单直接选六档或清除；菜单读回与页面重新打开后的结果一致。
2. 优先级与评级互不污染；历史字段、标签、印象、长测评、时长和其他平台信息保持完整。
3. 浏览、悬停、展开菜单和 Escape 关闭不产生写入；主动选状态或等级才保存。状态已保存、等级未设置时，不冒充两者都未保存。
4. 保存失败时有明确反馈，选择可重试，不出现“菜单已关闭所以用户以为保存成功”；保留原有修订冲突处理，不绕过 repository。
5. 键盘可进入、选择和退出，焦点能回到作品；鼠标菜单在窗口四角和矮窗口不越界，内容需要时可滚动。新增横向等级行的键盘路径清晰。
6. 网格、列表、折叠分组、搜索结果和规划视图的行为一致；回收站不出现不适用的状态操作，非游戏不出现游戏评级。
7. 更新真正受交互改变影响的测试，保留旧测试覆盖的独立字段、失败重试和持久化断言；不得简单删除失败断言来换取通过。

交付一个边界明确的候选分支/提交，附操作前后截图和实际测试结果。无需先等 Codex 画界面；遇到会改变业务语义的选择，只暂停那一项，继续上述确定范围。

## 六、ZD-03：状态与成果模型的短决策包（B2 / PD-01～03）

目标是把此前讨论变成所有者能快速选择的具体方案，不是今天直接改模型。最多比较两种主方案，并给出明确推荐：

1. 保留现有六态，用现有历史及有限交互增强表达。
2. 将“当前活动/计划”与“曾通关、全成就等成果事实”分开表达。

必须明确：暂时搁置与待体验的规划关系；持续游玩不等于一定曾通关；优先级与个人评价是两个维度；全成就与通关不能互相代替；“已放弃”不自动删除；未知不能推断成否。

用合成记录说明以下输入怎样显示、怎样编辑、是否允许评级、是否进入待体验规划、怎样排序：普通已通关；已通关且二周目；多次胜利的肉鸽；没有最终通关点的 MMO；已玩 30 小时但未通关且搁置；放弃；全成就；历史只有月份；旧 replaying 值；改状态前已存在 SSS 评价。

周目、单次胜利、完成日志和全成就分别定义，不用“完成记录数量减一”推算周目。自动记录日期如有必要，只讨论触发、确认、去重、撤销和补录，不实现后台自动写入。录入日期不冒充实际体验日期。

交付：一份短说明、场景矩阵、右键/详情的静态图或隔离原型，以及两种方案的数据兼容、旧版写入风险、备份与回退比较。明确列出最多三项需要所有者回答的选择，并指出哪些可以后置。不要创建八份空规范。

如所有者当日确认方案，先把确认范围记录到任务/决策，再拆独立实施任务；不要把一句“方案不错”扩张成全部迁移或自动化授权。未回复时设计包可以进入 REVIEW，继续其他任务。

## 八、ZD-05：批量收录与来源可靠性（B5 / PD-07～08）

Steam 批量收录是核心价值，现有免费官方 API 设置、库读取、预览、去重、时长和封面补齐已经存在。豆瓣书籍/影视 URL 导入也已存在；名称搜索尚无。不要因为没接触真实账号就说接口不存在，也不要再次手工导入数百游戏。

工作优先级：

1. 检查已有去重和保护私人字段的代码、测试，使用合成库存验证重复导入不会新增重复 AppID；同名不是充分去重依据。
2. 若发现已确认规则下的缺陷，做小修复。当前已有取消、并发和部分限流保护，先盘点再补，不重复造一套调度框架。
3. 给出来源请求可靠性的有限方案：超时、取消、同请求合并、短暂失败退避、429/401/403 处理、缓存范围与失效。可制作不接正式写入链的隔离实验，标清与真实官方接口的差别。
4. 研究豆瓣名称检索的可用来源、准确性、访问限制和维护成本；技术事实查官方资料/原始项目并注明日期。不可稳定实现就明确说明，保留页面 URL、手动输入和候选确认。
5. 为元数据刷新画出字段级差异预览：哪些是补缺，哪些是用户改过，哪些只建议更新。人工改名、个人评级、印象、测评和自选封面不被来源刷新默认覆盖。

不要求付费 AI，不绕过登录、验证码或访问控制，不读取浏览器凭据，不访问真实 Steam 库来完成测试。过往库存统计不是当前验收依据；明确区分“mock 库读取通过”和“真实账号在线验证”。

验收：至少一组可重复的合成去重/失败用例、当前能力和缺口说明、可落实到独立模块的实施建议。覆盖策略、持久化来源记录和缓存格式未经批准不正式落库。

## 十、代码、数据与验证规则

- 继续现有 Electron / React / TypeScript 架构，遵守 presentation → domain ← infrastructure。domain 不做 I/O，不让 UI 直接操作文件系统或桌面桥。
- 已有共享 IPC 契约和 tokens，不重新从零建设；不引入新状态库、数据库、云同步或全局样式层。行为不变的局部拆分单独提交，不与新功能混成大补丁。
- schemaVersion 保持 1；不新增存储字段、启动自动规范化或迁移。保留未知字段、修订冲突检查和现有原子保存、previous / daily 备份链。不要为避免测试失败绕开这些保护。
- 所有自动化用临时目录、合成库和独立浏览器上下文；不读写真实 AppData/QIYU，不扫描私密备份，不关闭用户正在运行的栖域。

- 开发过程中按影响运行专项。最终稳定的集成候选有代码变动时，执行一次完整 npm run test:workflow；若触及评级/箔面，再跑当前封面专项。改动后失败先修，不用无关全量重复运行填满时间。
- npm run test:workflow -- --list 只列阶段，不算运行。源码 GUI、模拟桥、原生 Electron、指定免安装成品、mock 网络与真实网络分别记结果；不得互相冒充。未跑的诚实标“未验证”。
- 不通过删测试、改弱断言、跳过失败或改成旧版 UI 来拿绿灯。新测试应覆盖用户行为、错误路径或兼容风险，不镜像实现细节。
- 纯文档只查事实、引用、授权状态和隐私，不重复跑 GUI。能复用已有工具就复用，避免临时引入大量开发依赖。

## 十一、审查、提交与打包

每个小闭环及时提交，提交应可独立理解、可回退。按单一模板记录范围；只在任务实际开始时建任务文件，不预填大量空表。更新 CHANGELOG 和任务表时由一个指定写入者处理，避免多 Agent 相互覆盖。

尽可能由未参与编写的 DeepSeek 或另一独立审查 Agent 审差异与失败路径，不强制等待 Codex。审查者身份和结论真实记录。没有非作者审查条件时照常完成分支、测试、提交和接力，但明确“待独立审查”；不自审自合，不把 REVIEW 写成 INTEGRATED。

可以在已授权的 Git 操作范围保存任务分支；推送失败保留本地提交并记清，不丢掉成果、不无限排查认证。外部发布和 main 合并仍按单独授权；GitHub API 的 403 不应用历史重写或恢复私密提交来解决。不要改变仓库可见性和许可证。

本日计划本身不要求发版。只有功能完成、验证满足并另有相应授权时，才做与实际源码一致的新版本交付；每次只做 Windows x64 免安装 ZIP，不制作安装器。先核对当前版本，避免覆盖同版本旧包或替换用户正在使用的目录。记录版本、被打包提交、测试范围和 SHA-256，不自动启动、不自动上传发行版。

## 十二、截止前必须完成的接力

到期前把新增、去敏的任务与交接信息写入受 Git 跟踪的 docs/tasks 下，并更新唯一任务表。不要放进被忽略的 docs/ZCODE_*.md，不提交真实导入清单、SteamID、API Key、本机用户名路径或未脱敏日志。原始截图/日志可留本机忽略目录，仓内摘要必须足够让他人独立理解结果。

交接使用 docs/process/TASK_TEMPLATE.md，至少包含：

1. base 分支/完整 SHA、任务分支/完整 HEAD、工作树是否干净；未提交文件逐项说明，先在自己的任务分支妥善保存，不丢弃原工作区内容。
2. 已完成、未完成、取消/受阻事项，分别对应验收标准；写明状态，不说“基本完成”。
