## 3. 修订后的产品规则：当前关系和成果分开

### 3.1 当前游玩关系

原稿四项略作修订：保留用户此前明确要求的“已放弃”，不能与通关后当前不玩合并。

| 普通选项 | 含义 |
| --- | --- |
| 计划游玩 | 下一次准备开始或继续，也可以是通关后计划重玩；主页面入口仍可叫“待体验计划” |
| 游玩中 | 目前在玩；不再要求在“持续游玩”和“已经通关”之间二选一 |
| 暂时搁置 | 已暂停，未来可能继续；保留已有时长 |
| 当前不玩 | 目前没有继续安排，可包含通关后休息；不推断作品质量差或永久放弃 |
| 已放弃 | 明确不再计划继续；不删除、不隐藏、不清除评级、时长或历史 |

内部允许历史“当前关系未记录”，不要给普通新建流程增加必填确认。旧已通关作品无法可靠推断现在是否还玩，不能强制映射为当前不玩。

“计划游玩”不再等于“从未玩过”。已通关+计划重玩是正常组合，不标为数据冲突。重复体验不新增一个与当前关系互斥的主状态：本期可在事件备注/周目文字中记录“开始二周目”，不增加自动周目计数或额外进行中布尔。

### 3.2 通关进度

独立四值：未记录/未确定、明确未通关、已通关、不适用。未知不是未通关。肉鸽、沙盒和网游由用户决定自己的通关目标，也可选不适用。

- 改当前关系不自动改变通关进度；改通关进度不自动改变当前关系。
- 已通关不自动设次数为 1，不自动生成日期/历史。
- 不适用不等于低评级，也不自动清次数或旧记录。
- 只有用户明确编辑成果或记录明确完成时才更新成果；Steam 库存、时长和普通日志不决定它。

### 3.3 优先级、个人评级与封面

继续沿用 SSS/SS/S/A/B/C、现有 playPriority/personalGrade 和两套手动顺序，不另造一套评分字段。

- 计划优先级适用于计划游玩/搁置；搁置仍在计划视图末层，不因优先级高挤到正常计划之前。
- 已通关作品无论当前在玩、搁置、计划重玩或已放弃，均可编辑个人评级，保留对应箔面。
- 不适用作品也允许个人评级，并使用同一评级箔面。未记录/未通关但已有历史评级，必须保留显示和编辑能力；本轮不强迫清理它。其他尚无评级的未通关作品不额外开放新评级资格。
- 已通关分档只按有效通关进度=已通关，不把不适用作品偷偷算作通关。
- 已通关+计划重玩可以同时出现在“待体验计划”和“已通关”两个视图，使用各自的等级和顺序，不互相覆盖。
- 改某个等级只在等级实际变化时清本维度顺序；改状态/进度不清另一等级，不规范化旧别名。
- 保留 SS/SSS 区分、现有对角反光与无网格网点规则。旧已通关作品的绿边、评级和箔面不能退化；新组合用紧凑活动图标/文字与独立通关标识表达，避免借机重做材质。活动与通关标记的颜色保持清晰。

## 4. 数据模型与兼容：先有统一读取，再接全部入口

新增最小可选结构，表达当前关系、通关进度、累计完成次数、明确完成事件。命名由你根据源码确定，避免与已有未知扩展冲突；不新增数据库或全局持久化键。原有 schemaVersion 仍为 1，旧 gamePlayState/status/experienceEntries 等保留。新增已知字段须有严格校验、未知扩展须可往返，不能因为 schema 没变就宣称旧版可安全写新版库。

统一领域纯函数读取有效值，新字段的明确值优先；只有字段缺省才回退旧字段。显式选择“未确定”需要能覆盖历史推导，不能删字段后又回退成已通关。

| 旧数据的有效状态 | 当前关系只读派生 | 通关进度只读派生 |
| --- | --- | --- |
| want | 计划游玩 | 未确定 |
| playing | 游玩中 | 未确定 |
| ongoing / replaying | 游玩中 | 未确定，不推断曾通关 |
| paused | 暂时搁置 | 未确定 |
| abandoned | 已放弃 | 未确定 |
| cleared，或没有 gamePlayState 且 status=finished | 当前关系未记录 | 已通关 |

只在缺少更具体旧值时按原通用 status 回退，不让 status=finished 覆盖明确的 gamePlayState。所有旧记录的次数和完成事件默认为未记录/无新事件，不能由 cleared 推成1次，也不扫描旧日志自动转换。

旧 cleared 的通关事实可可靠只读派生，不能让用户重新逐件确认后才恢复箔面和分档。显式保存一款时只改对应维度及必要的兼容保全，不给其他作品补默认值。

建议对已有作品冻结旧六态作为兼容来源，新操作写新维度，避免每次编辑再向有歧义的旧单轴模型反投影；新建时仍构造旧校验能接受的基础字段。如果确需更新旧投影，必须证明“旧 cleared 改为游玩中后，原通关事实仍完整保留”，不能更新旧轴后使另一维度的只读回退失效。新字段是新版事实来源，不让两套写入路径互相覆盖。将最终策略写入一页兼容说明。

必须完整接入：详情、右键、作品编辑器、批量编辑、排序/分档/拖动、卡片/列表、状态统计及游戏导入初态。非游戏板块沿原逻辑；不把新游戏规则复制给书影音。元数据补缺、时长、标签、隐藏/回收/恢复操作必须保留新旧数据原值。

启动/打开详情/搜索/排序/折叠/无修改关闭均不得写库。不损坏旧备份原文；所有保存继续走现有校验、修订冲突、原子替换和 previous/daily/导入前原文链。

本期仅承诺新版安全读取旧库、新版自身导出恢复完整；不承诺旧版能理解新增维度或新旧程序交替编辑。回退前分别保留升级前备份与新版完整导出，不能让恢复旧备份被描述为保留所有升级后修改。

## 5. 完成次数和明确完成事件：可编辑，不自动猜测

### 5.1 累计次数

可选非负安全整数；空=未记录，0=明确零次，N=用户明确填写的累计值。界面可设值、改值、清空；不根据普通 completed 日志、明确完成事件数量、时长、成就或当前关系计算总数。

累计值是唯一累计统计来源。事件列表只叫“已记录的完成事件”，不能把事件数再展示成另一个累计通关次数。直接改累计数不伪造历史事件、不默认补日期。若用户录入互相矛盾的信息，明确提示并允许手动修正，不静默改另一维度。

### 5.2 记录一次明确完成

采用独立可选完成事件类型/集合，避免为未知日期修改全部旧日志契约。事件至少有稳定唯一 ID、独立实际发生日期（可缺省）、录入时间和可选备注；可用文字记录周目/挑战，不做自动解析或完整挑战系统。

流程紧凑：点击“记录一次完成”→可选实际日期/备注→清楚预览对累计次数和通关进度的影响→一次保存。

- 累计已知 N：允许明确勾选同步+1，预览 N→N+1；不依赖点击次数。
- 累计未知：默认只记事件并保持未知，不能隐式把未知当0再加1；允许用户明确选择“从本次开始计为1”或填写包含本次的累计值。文字不能声称此前实际为0。
- 是否同时标记已通关须在确认区明示，可默认勾选；当前为“不适用”的作品默认保留不适用，可记录一次自定义完整体验，不能强改为通关。
- 不更改当前关系或累计时长。事件、明确选择的次数和进度变更一笔提交，失败全部不落库、保留草稿及稳定 ID。
- 同一个提交 ID 的双击/失败重试/重复调用不重复创建或增加。不同事件 ID 的人工再次记录不能靠文本猜重；疑似重复可提示但不自动吞掉。

### 5.3 编辑、删除、撤销

- 编辑日期/备注不重新+1；普通日志的增改删完全不碰累计数。
- 删除完成事件默认只删记录，明确提示累计数独立保留；若用户希望修正累计值，提供显式确认的数值修正，可同笔提交。不得按列表重算，也不能每次重开/删除自动扣减。
- 新完成操作成功后提供“撤销本次”：还原本次新增事件及本次造成的次数/通关进度变化。只撤销所属字段，不恢复整库旧快照；其他作品或个人文字不能被回滚。
- 若撤销前相关字段已被改动，禁止旧快照覆盖，提示手动修正；相同撤销不能反复减数。至少覆盖关闭重开详情仍能编辑/删记录，重启后事件/次数完整；本轮不要求永久操作历史或跨重启撤销队列。

### 5.4 日期

新完成事件实际日期：未知、YYYY、YYYY-MM、YYYY-MM-DD；日历合法，保留原精度，不补1月/1日，不以 recordedAt、收录时间或今天替代。默认实际日期未知，用户可一键选今天，但不能默认把补录当今天。

当前旧 ExperienceEntry.date 必填，校验只接受月/日精度，旧编辑器还默认今天。它是旧功能事实，不要把空日期或年份塞入旧数组来强行复用，不放宽全库旧日志校验。可以在详情时间线统一呈现，但保留源类型和对应编辑器；未知日期单独显示，不能靠录入时间冒充实际发生顺序。

## 8. 可见且真正隔离的演示模式（必须）

## 9. 执行顺序：先做可见主线，再完成闭环

最多两条写入任务，独立分支/worktree；只读评审另计。App、共享 controller、repository、IPC 各指定唯一写入者，接线串行。其他 Agent 可负责纯函数/次数模块或局部修复，不能同时改同一共享文件。

| 阶段 | 必须产出 | 判定 |
| --- | --- | --- |
| S0 快速准备 | 真实基线、简短映射与契约、工作区登记 | 不重做基线报告，不无限等待 |
