项目实际仍为 **0.4.23**，已有的收藏、Steam 连接、批量操作、分级计划和数据保护值得继续沿用。主要缺口是状态语义和快捷操作，不需要重做一遍现有功能，也没有足够依据更换技术栈或持久化方案。

## 6. 建议首批独立任务与验收标准

任务状态目前全部为 **PROPOSED（待批准）**。下面的工作范围不是自动授权；确认后每项建立单独分支、任务记录和评审。下列目录为建议边界，正式领取前仍检查实际文件和依赖。

### B0 — 接续成果审查与可复现基线（P0）

- 范围：已有 13 项未提交成果；仅脚本、CI、package 脚本和相关接续说明，不改 `src/`、`desktop/` 行为。
- 依赖：所有者允许处理既有未提交成果；独立审查。可由 DeepSeek 审查、Codex 集成，或反向分配，避免作者自审。
- 验收：逐项认定保留/修订/不集成理由；两个新脚本与 15 阶段入口一同纳入，入口不引用缺失文件；当前工作区无改动被静默丢弃；集成候选能在干净隔离 checkout 安装、单测、构建并完成对应关键流程。远程 runner 未验证时明确标记，不宣称 CI 通过。
- 回退：保持旧发布包；每个可审查提交单独回退。规范修订与测试修复拆开审阅，不提交秘密或原始私密证据。

### B1 — 正式基线与最小接力文档（P0）

- 范围：批准后迁入五份草案并修正本报告所列事实；补阅读指南、一个任务/交接模板；定向更新 `AGENTS.md`、ADR 状态及流程引用，不大批重命名历史文件。

- 验收：另一个 Agent 只读仓库即可识别当前版本、批准需求、未决项、任务状态、可执行下一步和禁区；没有互相矛盾的固定代理所有权；所有内部链接有效；去敏交接可被 Git 跟踪；无真实账号/收藏/本机身份。不会新增第二套并行的正式工作流。

### B2 — 游戏状态、成果与日期决策包（P1，设计任务）

- 验收：至少比较“维持现有六态并增强历史”与“当前活动/完成事实分开”两种方案，覆盖：巫师通关后不再玩、艾尔登法环二周目、杀戮尖塔多次胜利、无通关终点 MMO、30 小时未通关且搁置；另覆盖已放弃、全成就候选和旧 `replaying`。

- 交付条件：上述方案、场景与兼容样例齐全，进入 REVIEW；所有者选择方案是后续实现授权门槛。交付设计包不等于已授权实施迁移。

## 7. Codex 额度耗尽时的开发接力方案

本节是建议 SOP，待所有者确认后才纳入正式规范。

### 7.1 最少的仓库记录

不要求每轮阅读全部历史聊天，也不立即创建八套完整 SOP。先维护：

- 一个阅读入口：指向已批准 PRD、ADR、能力基线、工作流和任务表。
- 一个短任务表：任务编号、批准范围、负责人、独立评审人、依赖、分支/最新 SHA、状态、下一步。任务详情内直接包含下列交接字段，避免再写一份重复日报。
- 一个任务模板：同一份记录贯穿领取、实现、测试、交接和集成。后续文档只在真实触发时补充。

Git 中的批准记录与任务文件是接手依据；Issue/PR 链接用于讨论与评审。原始私密日志保留本机，公开任务内写去敏摘要与可复现命令。不能只留下“详见聊天记录”或不可访问的 `evidence/` 路径。

### 7.2 任务与分支规则

1. 任务从 PROPOSED 经所有者/预授权流程批准为 READY，随后为 IN_PROGRESS、REVIEW、INTEGRATED；受阻记录原因及其他可做任务，不把作者“完成”直接当合并。
2. READY 必须有已批准需求/决定、范围、禁止触碰模块、依赖和验收标准。重要产品决定、迁移、覆盖策略和 UI 大改不能借接力绕过确认。
3. 每个写入任务独立分支、独立 worktree；基于已审查基线。共享契约和集成文件由任务指定唯一写入者，保留现有两条并行写入上限。
4. 作者在分支提交并自测，独立评审者检查差异、测试与数据影响；未经审查不合并。合并后将准确 SHA 和相应验证结果回填任务表。
5. 发布与功能合并分开；没有发布批准不自动创建 Release 或上传包。发行保持免安装 ZIP。

### 7.3 Codex 离线时怎样继续

| 情况 | 可以继续 | 必须等待什么 |
| --- | --- | --- |
| 有 READY 任务 | DeepSeek 独立开发、测试、提交任务分支，准备可审查 PR；Zcode 做其明确领取的短任务 | 不必等待 Codex 恢复额度才写代码 |
| 需要跨任务接口调整 | 在任务记录中提出契约变化；其他不受影响任务继续 | 契约评审、所有权协调；重大语义由所有者确认 |
| Codex 无法评审，有其他合格独立评审者 | 指定非作者的 DeepSeek/Zcode 等按同一风险标准评审，记录意见及测试 | 临时集成/合并权需所有者预先或当次明确授予；不能因额度耗尽自动获得 |
| 只有作者在线，或没有合并授权 | 完成分支、验证、修复、研究和交接；领取其他批准且独立的任务 | 不自审自合；集成等待独立评审/明确授权，但项目其他准备工作不停止 |
| 发现数据损坏、需求歧义或重大风险 | 保存合成复现、风险说明和安全回退建议，继续无关任务 | 相关高风险写入等待决定，不拿真实收藏实验 |
| Zcode 限时额度即将结束 | 提前交付一个可复现小成果；提交已能审阅部分，明确未完项 | 不为赶额度把半成品或未经测试的代码塞入主分支 |

所有者可在规范批准时选择是否预授权“独立评审通过后的常规低风险合并”及其代理人；**本报告不假定已有这项授权**。未选择时按现有批准边界执行。

### 7.4 标准交接模板（建议嵌入每个任务文件）

```text
任务：编号 / 标题 / 状态 / 作者 / 独立评审人
批准依据：PRD/决定编号、批准人和日期；待确认事项

基线：基准分支 + 完整 base SHA
成果：任务分支 + 完整 HEAD SHA；worktree（私有路径单独留本机）
工作区：是否干净；未提交文件/补丁位置及保留方式

已完成：具体行为与验收条目对应关系

验证：被测 SHA/未提交差异、命令、时间、退出码、结果摘要
      区分单测/GUI/成品/mock/真实网络；未运行项目写明
证据：入库去敏摘要/合成夹具；私密原始日志位置另存本机
```

没有数据结构变更也应写明；代码可回退不等于新版数据能交给旧程序写，恢复必须遵循兼容文件，保留当前完整导出及升级前可读备份，不清字段、不自动重置。

### 7.5 Codex 恢复后的接管步骤

1. 读取任务表和变更后的 ADR/PRD，只读检查当前分支、SHA、工作树；不先重读全部历史文档。
2. 从上次已审查基线比较新增提交；按依赖检查任务边界、独立评审、测试摘要和未决事项。
3. 优先复核共享接口、数据写入和失败路径；只对缺证据、风险高或发生冲突的部分追加检查，不无差别重跑全部历史验证。
4. 对待合并任务给出通过/修改/拆分结论；按授权集成，更新能力基线和任务状态。已被代理集成的成果同样检查，不因作者变化重写。
